# Агент анализа события

Один агент с собственным конечным автоматом (`backend/app/agents/`). Готовые агентные фреймворки не
используются (условие кейса, стр. 18). Решения о шагах принимает разрешённая LLM, выполняет их код;
каждый шаг попадает в журнал `AgentTrace`.

```
PLAN ──► TOOLS ──► SYNTHESIZE ──► VERIFY ──┬─► FINALIZE (verified / partial)
  ▲                    ▲                    │
  │                    └──── REVISE ◄───────┘  есть ошибки или устранимые предупреждения
  └ при сбое LLM — план по умолчанию           (до 2 итераций, до 10 вызовов инструментов)
```

## Шаги
1. **PLAN** — LLM получает цель, событие и каталог инструментов со схемами аргументов и возвращает
   план до 6 шагов. Неизвестный инструмент или неверные аргументы → план отправляется на исправление.
   Политика агента всегда ставит первыми `get_company_profile` и `assess_relevance` (в журнале видно,
   что добавлено политикой). Если LLM недоступна — план по умолчанию.
2. **TOOLS** — выполнение шагов. Ошибка инструмента не роняет анализ: шаг помечается `error`.
3. **SYNTHESIZE** — `analyze_event`: LLM пишет инсайт по контракту v2, ссылаясь только на
   собранные доказательства (`evidence`).
4. **VERIFY** — детерминированные проверки (`verify.py`), без LLM. Перед проверкой код сам
   переводит в AI_INFERENCE утверждения FACT с явным выводом («поэтому», «может», «зависит»): модель
   повторяет эту ошибку и после замечания, а исправление однозначное. В журнале это видно как
   «FACT → AI_INFERENCE: N».

   | Код | Уровень | Что проверяется |
   |---|---|---|
   | `unsupported_number` | ошибка | число в выводе отсутствует во входных данных (идентификаторы вроде `U_9250` не считаются) |
   | `unsupported_year` | предупреждение | год в выводе отсутствует во входных данных |
   | `outdated_bank_forecast` | ошибка | вывод повторяет прежний прогноз банка как текущий, хотя банк его пересмотрел (например, ставка 13,5% вместо 14,0%); допустимо, если сказано «ранее» или «пересмотрел» |
   | `relevance_without_company_data` | ошибка | причины релевантности не опираются на признаки компании |
   | `bank_claim_not_supported` | ошибка | тезис банка не подтверждается текстом процитированного фрагмента |
   | `payments_as_revenue` | ошибка | выручка выводится из платёжных данных |
   | `single_company_factor` | предупреждение* | использован один признак компании при нескольких доступных |
   | `bank_not_searched` | предупреждение* | аналитика банка не запрашивалась |
   | `bank_unused` | предупреждение* | материалы банка найдены, но не использованы |
   | `fact_contains_inference` | предупреждение | утверждение FACT содержит вывод («может», «зависит»…); исправляется кодом до проверки |
   | `unknowns_missing` | предупреждение | в профиле есть пропуски, а `unknowns` пуст |

   \* агент пытается устранить их повторной итерацией.
5. **REVISE** — если для исправления нужны новые данные (аналитика банка не запрашивалась), LLM
   выбирает: вызвать инструменты (например, поиск по банку), переписать анализ или остановиться.
   Если замечания только к тексту (числа без источника, один признак компании и т.п.), новые данные
   не помогут — код сразу отправляет анализ на переписывание, без лишнего запроса к LLM.
   Переписанный анализ идёт мимо кеша.
6. **FINALIZE** — `quality_status = verified`, если ошибок нет, иначе `partial`; все замечания —
   в `quality_issues`, журнал и инсайт сохраняются.

## Инструменты
| Инструмент | Что делает |
|---|---|
| `get_company_profile` | профиль, продукты, ФТС, платежи, пропуски данных |
| `get_company_relations` | группа компаний и концентрация платежей |
| `assess_relevance` | объяснимый балл 0–100 и совпадения события с признаками компании (`docs/scoring.md`) |
| `search_bank_research` | поиск тезисов в аналитике Альфа-Банка (BM25, свежие обзоры чуть выше старых) |
| `get_bank_forecasts` | актуальные прогнозы банка (ставка, инфляция, курс, ВВП) по каналам события; пересмотренные — с прежним значением и датами. Для событий про ставку, инфляцию, курс и спрос добавляется политикой агента |
| `get_official_rates` | текущая ключевая ставка и официальные курсы юаня, доллара и евро по данным Банка России — FACT со ссылкой на cbr.ru. Для событий про ставку, курс, инфляцию и внешнюю торговлю добавляется политикой агента; `CBR_DATA_ENABLED=0` — выключить |

Чат уточнений (`chat.py`) дополнительно использует детерминированный **сценарный расчёт**
(изменение процентных расходов = долг × Δставки / 100) — только по числам, которые назвал пользователь.

## Безопасность
- Все инструменты **только читают** данные; переводов, изменений и внешних действий нет.
- Компания фиксируется запросом: агент не может передать в инструмент другой `company_id`.
- Изоляция в API: `X-Company-Id` ограничивает ресурс, а при `DEMO_AUTH_REQUIRED=1` подписанный Bearer-токен
  подтверждает demo-сессию и список доступных компаний; чужие ресурсы → 403.
- Тексты новостей, документов банка и вопросы пользователя передаются модели как данные
  (`<news>`, явная инструкция игнорировать команды внутри). Синтетическая новость №10 проверяет это.
- Загрузка статей по URL — защита от SSRF (только http/https, только публичные IP, проверка редиректов, лимиты).
- Лимиты: до 10 вызовов инструментов и 2 итераций на анализ, суточный лимит запросов к LLM,
  ключ API только в `backend/.env`, ключ вычищается из сообщений об ошибках.
- Журнал: каждый вызов LLM (модель, токены, стоимость, ошибки) — `backend/var/llm.sqlite3`;
  каждый шаг агента — `AgentTrace` в `backend/var/app.sqlite3`. Скрытые рассуждения модели не сохраняются.

## Несколько публикаций об одном событии
Склейка (`docs/news-dedup.md`) собирает издания об одном событии. У каждой публикации сохраняется своё начало
текста (`EventSource.summary`), и в доказательства разбора она идёт отдельно — `event.source.N` со своим
изданием, ссылкой и датой: цитата не уходит к чужой ссылке.

`app/modules/news/corroboration.py` сверяет цифры между **независимыми изданиями** (по домену: перепечатки
одного издания не подтверждают друг друга). Из каждой публикации берутся проценты и суммы с показателем
(«ставка 14%», «инфляция 6,1%», «пошлина 10%»; показатель — ближайшее к числу слово в том же предложении):
- `event.confirmed.N` — цифру назвали два и больше изданий: «Ключевая ставка 14% — подтверждено 2 изданиями»;
- `event.conflict.N` — для одного показателя издания называют разные цифры и ни одной общей.

Промпт: спорную цифру не подавать как факт — назвать оба значения или указать, что источники расходятся.
Проверка `disputed_fact` (ошибка): утверждение FACT содержит спорную цифру без оговорки.

## Статусы проверки
Проверка детерминированная: она не оценивает экспертную правильность вывода. Поэтому `verified` в интерфейсе —
**«Проверено автоматически»**: числа найдены в источниках, ссылки существуют, прогнозы банка актуальны,
спорные цифры с оговоркой.

| Статус | Когда |
|---|---|
| `verified` — «Проверено автоматически» | замечаний-ошибок нет |
| `partial` — «Есть замечания проверки» | остались ошибки, не относящиеся к актуальности и противоречиям |
| `outdated` — «Позиция банка могла устареть» | остался устаревший прогноз банка (`outdated_bank_forecast`) или позиция банка взята из документа, а по теме найден документ новее на 30+ дней (`stale_bank_document`) |
| `conflicting` — «Источники расходятся» | осталась спорная цифра, поданная как факт (`disputed_fact`) |

`stale_bank_document` — предупреждение, на которое агент делает повторную итерацию; если позиция банка так и
осталась из старого документа, статус — `outdated`. Итог считает `verify.final_status`.

## Качество
`backend/scripts/run_eval.py`: доля проверенных автоматически инсайтов и разбивка по статусам (`status_counts`), повторов, найденной позиции банка,
чисел без источника, различие выводов разных компаний по одному событию, precision@5 ленты
по ручной разметке (`data/synthetic/relevance_labels.json`). В продакшене те же метрики считаются
по журналам и отзывам «Полезен ли анализ?» (`/api/v1/system/status`).

## Ролевой слой: «Что это значит для вас»
Разбор события общий для компании, а читают его разные люди (задание: сервис для людей, а не для юрлиц).
`app/agents/role_view.py` — короткий отдельный запрос к модели поверх готового разбора для роли смотрящего
(`X-User-Role` или `?role=`; роли и их задачи — `app/modules/personalization/roles.py`):
- `headline` — что событие значит для задач этой роли;
- `points` — 2–3 вывода с метками FACT/BANK_ANALYSIS/AI_INFERENCE/HYPOTHESIS;
- `risk_order` — риски разбора в порядке важности для роли;
- `next_steps` — до трёх шагов именно для этой роли.

Проверка `check_role_view`: ссылки только на доказательства разбора, никаких новых чисел, `risk_order` — только
названия рисков разбора; при ошибке — повтор с замечаниями. Без LLM (нет ключа, исчерпан бюджет) — по правилам:
риски и шаги со словами задач роли поднимаются наверх (`method: rules`). Блок хранится по паре «разбор × роль»
(таблица `role_views`): повторный просмотр бесплатный. `GET /api/v1/insights/{id}/role-view`, `?refresh=true` —
пересчитать.

## Положение компании в отрасли
`app/modules/companies/position.py` (п. 1 задания: «положение в отрасли и доля рынка»). Рынка целиком в данных нет,
поэтому позиция — **по выборке банка**: среди компаний того же класса ОКВЭД с известной выручкой (заглушка 1000 руб.
не считается): место по выручке, перцентиль, доля в выручке отрасли по выборке, уровень (лидер — топ-10%, крупный —
топ-25%, средний, небольшой) и то же для группы компаний. Меньше 5 компаний с выручкой в классе — `too_few_peers`.
В профиле — `industry_position`, в доказательствах агента — `company.position` (FACT), в интерфейсе — строка
«Положение в отрасли» в профиле компании.
