# ВышКат

Консольное приложение на C++ для учёта парка проката «ВышКат». На баланс ставится транспорт и инвентарь (шлемы, зарядные и док-станции). Перед приёмкой каждый объект проходит техосмотр.

## 2. Запуск
**Требования:** компилятор с поддержкой C++17 и CMake 3.16 или новее. Для тестов нужен GoogleTest: CMake берёт установленный в системе (`sudo apt install libgtest-dev`) или скачивает версию 1.14 при первой настройке (нужен интернет).
 
### Linux
 
```bash
cmake -S . -B build
cmake --build build
./build/vyshkat
```
 
**Тесты:**
 
```bash
ctest --test-dir build --output-on-failure
```
 
**Покрытие (GCC/Clang):**
 
```bash
cmake -S . -B build-cov -DCMAKE_BUILD_TYPE=Debug -DVYSHKAT_COVERAGE=ON
cmake --build build-cov
ctest --test-dir build-cov --output-on-failure
gcovr -r . --filter 'src/' --exclude 'src/main.cpp'
```
 
Для `gcovr` нужна установка: `pip install gcovr` (или `sudo apt install gcovr`). Результаты измерения приведены в разделе 10.
 
### Параметры CMake
 
| Параметр | По умолчанию | Назначение |
|---|---|---|
| `-DCMAKE_BUILD_TYPE=Debug` / `Release` | не задан | Тип сборки. Для покрытия нужен `Debug` |
| `-DVYSHKAT_BUILD_TESTS=ON` / `OFF` | `ON` | Собирать ли юнит-тесты. `OFF` убирает зависимость от GoogleTest |
| `-DVYSHKAT_COVERAGE=ON` / `OFF` | `OFF` | Инструментирование для измерения покрытия (только GCC/Clang) |
 
Пример сборки только приложения, без тестов: `cmake -S . -B build -DVYSHKAT_BUILD_TESTS=OFF`.
 
### Windows
 
```powershell

.\build\Debug\vyshkat.exe
ctest --test-dir build -C Debug --output-on-failure
```
 
Для CLion достаточно выполнить `Reload CMake Project` и запустить цель `vyshkat_tests`.
 
### Кодировка
 
Исходники в UTF-8, для MSVC в CMake включён флаг `/utf-8`. В `main.cpp` функция `setupConsoleUtf8()` переключает консоль Windows на UTF-8. Если русский текст всё равно отображается искажённо, выполните перед запуском `chcp 65001`.

**Меню:**

```
1. Принять транспорт
2. Принять вещь
3. Удалить из парка по инвентарному номеру
4. Число единиц в парке: всего, транспорт, вещи
5. Суммарное суточное потребление энергии
6. Техника, подходящая новичкам
7. Список техники и вещей с инвентарными номерами
8. Демонстрационный сценарий
0. Выход
```

При приёме объекта программа спрашивает инвентарный номер, название, состояние (1 — новое, 2 — хорошее, 3 — требует ремонта, 4 — сломано, 5 — списано) и данные конкретного вида (простоту 1–10, расход энергии в кВт·ч в сутки, размер шлема).

```
src/
├── main.cpp                  точка входа

│   ├── ConsoleApp            меню и вывод

├── di/
│   └── DiContainer.h         DI-контейнер
├── enums/                    EquipmentCondition, InspectionResult
├── interfaces/               Inventoriable, EnergyConsumer, InspectionService
├── models/
│   ├── Asset                 общая база инвентарных объектов
│   ├── transport/            Transport, Scooter, Bicycle, ElectricScooter, ElectricBicycle
│   └── items/                InventoryItem, Helmet, ChargingStation, DockingStation
├── inspection/               Inspection, ServiceCenter
├── park/                     Park, ParkService, ParkReport
├── factory/                  Factory<T>, TransportFactory, ItemFactory
└── reader/                   InputReader, ConsoleInputReader

tests/
├── fakes/                    подмены: FakeInspectionService, FakeInputReader
├── support/                  построители объектов, перехват вывода
└── models/ inspection/ park/ factory/ reader/ di/ app/    тесты по модулям
```

Границы модулей:

- **`models`** не знает ни о парке, ни о техосмотре, ни о вводе.
- **`park`** зависит от `interfaces` и `models`, но не от `ServiceCenter`. Реализацию техосмотра он знает только через интерфейс.
- **`inspection`** содержит рабочую реализацию техосмотра. Её создаёт только `AppContainer`.
- **`app`** — единственный слой, который знает о конкретных классах и связывает их.

| `Helmet`                             | Шлем с размером                                                                                                     |
| `ChargingStation`                    | Зарядная станция. Реализует `EnergyConsumer`                                                                        |
| `DockingStation`                     | Док-станция                                                                                                         |
| `EquipmentCondition`                 | Состояние: `NEW`, `GOOD`, `NEEDS_REPAIR`, `BROKEN`, `RETIRED`                                                       |

|---------------|-----------------------------------------------------------------------------------------------------------------------------|

| `ParkReport`  | Отчёты только для чтения: число единиц (всего, транспорт, вещи), энергия, список для новичков, список всех объектов         |

| Тип                  | Что делает                                                                                                        |

## 6. Логика решений

**Единая база для транспорта и вещей.** Транспорт и вещи стоят на балансе одинаково, поэтому оба наследуют `Asset` и реализуют `Inventoriable`. `Park` хранит их в одном списке и по одному номеру. Сотрудники на баланс не ставятся (по условию), поэтому не наследуют `Asset` и в иерархию не входят.

**Энергия как отдельный интерфейс.** Потребляют энергию объекты из разных веток: электротранспорт и зарядная станция. Общий интерфейс `EnergyConsumer` позволяет суммировать расход, не зная конкретных типов.

**Простота хранится в `Transport`.** По заданию правило «для новичков» относится к прокатной технике, то есть к транспорту. Вещи (шлем, станция) новичкам не «выдаются» в этом смысле, поэтому поле простоты у них не нужно. Порог 6 вынесен в константу `ParkReport::kBeginnerMinSimplicity`.

**Единственный путь на баланс.** Добавить объект в парк можно только через `ParkService::accept`. Порядок действий: проверить, что объект не пустой и номер свободен, провести техосмотр, добавить при `PASSED`. Отклонённый объект не занимает номер. Дубликат отклоняется до техосмотра: это ошибка данных, а не результат осмотра.

**Что осматривает `ServiceCenter`.** Только состояние: `NEW` и `GOOD` проходят, `NEEDS_REPAIR`, `BROKEN` и `RETIRED` нет. Правило одинаково для транспорта и вещей. Причина отказа хранится в `Inspection::getReason()` и выводится в консоли («Причина: …»).

**Новый вид добавляется регистрацией.** Фабрика хранит словарь «название вида → функция-создатель». Каждый создатель сам запрашивает у `InputReader` данные, нужные именно его виду: самокат спрашивает простоту, электросамокат ещё и расход энергии. Общей структуры «со всеми полями» нет. Меню видов строится из `types()`, поэтому консоль не меняется при добавлении вида.

**Ввод вынесен за интерфейс.** Создатели и консоль не используют `std::cin` напрямую. Это даёт тестируемость и изолирует остальной код от способа ввода.

**Обработка ошибок.** Неверные данные (пустое поле, простота вне 1–10, отрицательная энергия) вызывают `std::invalid_argument`. `ConsoleApp` перехватывает его и выводит сообщение, программа продолжает работать. Конец ввода приводит к тихому выходу из меню.

**Русский текст только для показа.** Названия видов (`getKind()`) и меню используются для вывода. Логика на них не опирается: вид выбирается по номеру в списке, а не сравнением строк. Поэтому сбой кодировки ухудшит внешний вид, но не поведение.

## 7. Паттерны и внедрение зависимостей

| Паттерн                                             | Лекция           | Где                                                                      | Зачем                                                                                               |
|-----------------------------------------------------|------------------|--------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------|
| **Фабричный метод** (вариант с реестром создателей) | 4. Порождающие   | `Factory<T>`, `TransportFactory`, `ItemFactory`                          | Новый вид создаётся без правки существующего кода. Создатель инкапсулирует, какие данные нужны виду |
| **Стратегия**                                       | 5. Поведенческие | `InspectionService` ← `ServiceCenter`                                    | Правило приёмки заменяемо: рабочая реализация и заглушка в тестах взаимозаменяемы                   |
| **Фасад**                                           | 6. Структурные   | `ParkService`                                                            | Консоль работает с одной точкой входа и не знает о `Park` и техосмотре. Нельзя обойти осмотр        |
| **Внедрение зависимостей**                          | 2. DI            | `ParkService`, `ConsoleApp`, `Factory<T>`, `DiContainer`, `AppContainer` | Классы получают зависимости снаружи, а не создают их сами                                           |

**Как устроен DI.**

- Классы принимают зависимости через конструктор (`ParkService(Park&, InspectionService&)`, `ConsoleApp(...)`). Это внедрение через конструктор: без глобальных объектов и синглтонов.
- `DiContainer` хранит способы создания сервисов по их типу и отдаёт один экземпляр на тип. Создание ленивое: сервис появляется при первом `resolve()`. Зависимости создатель берёт сам, вызывая `resolve()`. Циклические зависимости и обращение к незарегистрированному типу дают `std::logic_error`.
- `AppContainer` — composition root. Это единственное место, где рабочие реализации связываются с интерфейсами (`InspectionService` → `ServiceCenter`, `InputReader` → `ConsoleInputReader`).
- Любой сервис заменяется до первого `resolve()`: `app.services().registerInstance<InspectionService>(stub)`. Так тесты подменяют техосмотр.
- Контейнер написан самостоятельно (около 90 строк). Готовая библиотека (например, Boost.DI) добавила бы тяжёлую зависимость ради нескольких регистраций.

**Что сознательно не применялось.** Singleton: вместо него DI, поэтому глобального состояния нет (в `DiContainer` экземпляр один на контейнер, но это область жизни, а не паттерн). Builder, Decorator, Composite, Observer: в этой задаче им нечего решать, а добавление ради паттерна считается overengineering.

## 8. Принципы SOLID

**Принцип единственной ответственности (SRP).** Каждый класс отвечает за одно:

- `Park` хранит и следит за уникальностью номера.
- `ParkService` оркеструет приёмку.
- `ServiceCenter` принимает решение по осмотру.
- `ParkReport` считает отчёты.
- `Factory<T>` создаёт объекты.
- `ConsoleInputReader` читает ввод.
- `ConsoleApp` отвечает за диалог.

*Где ограничен:* `ConsoleApp` совмещает меню, вывод и разбор выбора. Для консольного слоя это допустимо, разбивать его на отдельные классы меню и вывода было бы излишним.

**Принцип открытости/закрытости (OCP).** Новый вид транспорта или вещи добавляется классом-наследником и одной регистрацией создателя в `AppContainer::registerTransportTypes` / `registerItemTypes`. `Park`, `ParkService`, `ParkReport` и `ConsoleApp` не меняются. Новый потребитель энергии (любой класс с `EnergyConsumer`) попадает в отчёт автоматически.

*Где ограничен:* `ParkReport` использует `dynamic_cast` (см. 
z
вопрос 2). Регистрация видов тоже требует правки `AppContainer`, но это единственное место, которое для этого предназначено.

**Принцип подстановки Лисков (LSP).** Любой наследник `Transport` или `InventoryItem` можно использовать там, где ожидается `Asset` или `Inventoriable`. Инварианты (непустой номер, простота 1–10) проверяются в конструкторе базы, наследники их только дополняют своими проверками (`dailyEnergyKwh >= 0`). `Park`, `ParkService` и `ParkReport` работают с интерфейсами и не зависят от конкретного типа. `FakeInspectionService` и `ServiceCenter` взаимозаменяемы для `ParkService`.

**Принцип разделения интерфейсов (ISP).** Интерфейсы узкие: `Inventoriable` (3 метода), `EnergyConsumer` (1), `InspectionService` (1), `InputReader` (3). Объект реализует только те, что ему нужны: шлем не обязан возвращать энергию, а электросамокат наследует оба контракта.

*Где ограничен:* в `Inventoriable` нет `getKind()`, поэтому `ConsoleApp::submit` работает с `Asset`, чтобы показать вид объекта. Раздувать общий интерфейс ради вывода я не стал.

**Принцип инверсии зависимостей (DIP).** `ParkService` зависит от `InspectionService`, а не от `ServiceCenter`. Фабрики и `ConsoleApp` зависят от `InputReader`, а не от `std::cin`. Связывание делает `AppContainer`.

*Где ограничен:* `Park`, `ParkService` и `ParkReport` не имеют своих интерфейсов, `ConsoleApp` зависит от них напрямую. У них одна реализация, и интерфейс ради интерфейса был бы «декоративным» SOLID. Инверсия сделана только там, где реально есть вариативность: техосмотр и ввод.

## 9. Ответы на обязательные вопросы

### 1. Какой принцип SOLID применён наиболее явно и где

**Инверсия зависимостей (DIP).** `ParkService` (`park/ParkService.h`) принимает `InspectionService&` (`interfaces/InspectionService.h`) и ничего не знает о `ServiceCenter` (`inspection/ServiceCenter.h`). Реализацию выбирает `AppContainer::registerServices()`. Решение о приёмке принимает подставленный объект, а не `ParkService`: это подтверждают тесты (вопрос 4). Второй явный пример: `Factory<T>` и `ConsoleApp` зависят от интерфейса `InputReader`.

### 2. Какой принцип сознательно ограничен или «почти нарушен» и почему это приемлемо

**Открытость/закрытость, из-за `dynamic_cast` в `ParkReport`** (`park/ParkReport.cpp`). Метод `totalDailyEnergyKwh()` определяет потребителей через `dynamic_cast<const EnergyConsumer*>`, а `beginnerFriendly()` выбирает транспорт через `dynamic_cast<const Transport*>`. Это RTTI в одном месте.

Почему я так сделал: `Park` хранит разнородные объекты как `Inventoriable`. Альтернативы хуже:

- Добавить в `Inventoriable` методы `getSimplicity()` и `getDailyEnergyKwh()`. Это нарушает ISP: шлем был бы вынужден возвращать 0 и «простоту» без смысла.
- Хранить отдельные списки потребителей и транспорта. Это усложняет `Park`, и дубликаты номера придётся проверять сразу в нескольких списках.

Это приемлемо, потому что:

- RTTI сосредоточено в одном классе, который только читает.
- Новые потребители энергии подхватываются без правок.
- Поведение зафиксировано тестами `ParkReportTest`.

Нарушение проявится, только если появится принципиально новый критерий отчёта (не энергия и не простота): тогда придётся добавить метод в `ParkReport`.

Другие сознательные компромиссы описаны в разделе 8: DIP применён только к реальным точкам вариативности, `ConsoleApp` совмещает несколько обязанностей, а в `Asset` есть русский текст для показа.

### 3. Что сломается или не сломается при расширении

| Расширение                                      | Что нужно сделать                                                                                                                | Что не меняется                                                                                                                                | Что может сломаться                                                                                                                                                                                                                         |
|-------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Новый вид транспорта** (например, гироскутер) | Класс-наследник `Transport` (и `EnergyConsumer`, если электрический) и одна регистрация в `AppContainer::registerTransportTypes` | `Park`, `ParkService`, `ParkReport`, `ConsoleApp`, тесты. Меню строится из `types()`, электрический вид попадает в сумму энергии автоматически | Ничего: компилятор не требует правок в других местах. Забытая регистрация проявится тем, что вида нет в меню                                                                                                                                |
| **Сотрудники**                                  | Отдельный класс `Employee` и свой список. Не наследовать `Asset` и не класть в `Park`                                            | Весь существующий код. Отчёты не считают сотрудников единицами парка, как и требует задание                                                    | Сломается, если сделать `Employee` наследником `Asset`: `Park` начнёт хранить их на балансе, а `countUnits()` их посчитает                                                                                                                  |
| **Склад запчастей**                             | Класс `SparePart : InventoryItem` и регистрация в `registerItemTypes` для единичных деталей                                      | `Park`, `ParkService`, `ParkReport`                                                                                                            | Учёт по количеству не ложится на `Park`: он требует уникальный номер у каждого объекта, а партия одинаковых деталей имеет один номенклатурный номер. Для такого учёта нужен отдельный класс (например, `Warehouse`), а не расширение `Park` |
| **Новое правило осмотра**                       | Новый класс, реализующий `InspectionService`, и регистрация вместо `ServiceCenter`                                               | `ParkService`, `Park`, тесты `ParkService`                                                                                                     | Тесты `ServiceCenterTest` относятся к старому правилу и перестанут подходить                                                                                                                                                                |

**Собственный вариант расширения: станция аренды.** Класс `RentalStation` получает список техники и выдаёт её клиентам. Для выбора техники новичку используется то же правило «простота ≥ 6». Если правило усложнится (учёт состояния, возраста клиента), его стоит вынести из `ParkReport::beginnerFriendly` в отдельный объект-стратегию. Остальной код не пострадает: правило сейчас сосредоточено в одной константе и одной проверке.

### 4. Какой тест фиксирует решение техосмотра и правило «для новичков»; как подменяется зависимость

- **Решение техосмотра:** `ParkServiceTest.TrustsInspectionAndAcceptsBrokenItemWhenStubPasses` и `ParkServiceTest.TrustsInspectionAndRejectsGoodItemWhenStubFails` (`tests/park/ParkServiceTest.cpp`). Первый принимает сломанный объект, потому что заглушка сказала «пройден», второй отклоняет исправный по сигналу «отказ». Вместе они доказывают, что решает `InspectionService`, а не `ParkService`. Правило самого `ServiceCenter` фиксирует `ServiceCenterTest`.
- **Правило «для новичков»:** `ParkReportTest.SimplicitySixIsFriendlyToBeginners`, `SimplicityFiveIsNotFriendlyToBeginners`, `SimplicityTenIsFriendlyToBeginners` и `BeginnerThresholdIsSix` (`tests/park/ParkReportTest.cpp`). Они проверяют границу 5/6.
- **Как подменяется зависимость:** класс `FakeInspectionService` (`tests/fakes/FakeInspectionService.h`) реализует `InspectionService`, возвращает заданный результат и запоминает, какие объекты осматривали. Он живёт в `tests/`, не в `src/`. Передаётся двумя способами:
  - напрямую в конструктор: `ParkService service{park, inspection};`;
  - через DI-контейнер: `app.services().registerInstance<InspectionService>(stub);` (`AppContainerTest.StubReplacesInspectionAndRejectsGoodItem`).

## 12. Допущения и ограничения

- Состояние парка хранится только в памяти и не сохраняется между запусками.
- Правило «для новичков» применяется только к транспорту.
- Техосмотр оценивает только состояние. Причина отказа хранится в `Inspection` и выводится в консоли.
- Список состояний фиксирован (пять значений).
- Названия видов в меню (русский текст) задаются при регистрации в `AppContainer`.
- Правила осмотра и порог новичков заданы в коде, а не в файле настроек.
